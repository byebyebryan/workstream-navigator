Status: corrective production pass recorded; follow-up confirmation pending —
2026-08-07.

Post-run live process inspection falsified the original cleanup assertion: 13
OpenCode TUIs from repeated D8.2 runs had survived private-tmux removal, each
remaining runnable at roughly one CPU core with deleted PTY/state descriptors.
The original harness ignored park failures, asserted only momentary root
absence, and did not retain or verify provider PID identity. The functional
Fork/recovery evidence remained valid, but D8.2 cleanup was reopened pending
the correction and rerun described below.

The corrective operator-gated rerun on 2026-08-07 passed every local and real
loopback-SSH assertion. Local and SSH Fork each returned a distinct exact
same-provider session; lost-Runtime recovery retained the source session while
replacing generation, endpoint, provider process, and observer. Both host paths
parked cleanly, WSNav state excluded provider content, ordinary tmux state was
unchanged, and final cleanup removed every disposable process, socket, state
root, provider root, repository, authentication copy, and SSH artifact.

An earlier corrective rerun stopped after the local path with a generic
`cleanup-incomplete` result even though fallback cleanup left no live process
or socket. The harness had overwritten the primary failure and returned only a
boolean root-reference result. Bounded diagnostics then identified a mapped
root reference owned by the Python acceptance process itself, not a managed
Runtime or OpenCode process. Root inspection now excludes only that exact
cleanup-authority PID; parents, siblings, children, and shared process groups
remain external evidence. A deterministic regression keeps a root-owned
descriptor open in the harness while proving that an external process is still
reported. Primary failures and bounded sanitized cleanup diagnostics are now
retained separately, and root-wide validation runs after every exact cleanup
target has been attempted.

This operator-gated run used real OpenCode `1.18.11`, tmux `3.7b`, the
production WSNav candidate, and a real unprivileged loopback OpenSSH daemon.
The harness used one harmless turn with the low-cost

Every repository, OpenCode XDG root and authentication copy, WSNav host/client

## Corrective cleanup implementation and final rerun

Host schema 12 persists `Runtime.provider_pid` atomically with process birth.
Before launch it also proves that the pane/provider is its process-group leader.
Park stops the exact observer, terminates the revalidated provider group with
bounded TERM/KILL, and only then removes the private tmux server. Lost-Runtime
recovery applies the same cleanup before reserving a replacement generation.
Missing, changed, inaccessible, or malformed identity fails closed without
signaling an unrelated process.

The new disposable lifecycle fixture makes both the provider and a same-group
descendant ignore terminal hangup/TERM. It proves recovery and Archive remove
the complete group, retain ordinary tmux state, and leave no disposable root or
helper. This deterministic gate passes, and the corrected real local and
real-loopback-SSH production harness produced a complete passing run.

The temporary OpenCode server used to create a blank session receives bounded
exact cleanup on every returned action path; inconclusive cleanup is
recovery-required and non-retryable. The guardian now retains exact cleanup
authority across abrupt loss of the owning WSNav action, and the
kill-at-creation-boundary acceptance closed that corrective gate before the
operator rerun. Independent simultaneous loss of both action and guardian
remains outside the V1 in-process boundary.

## Acceptance-driven corrections

The first run exposed two real lifecycle races without relaxing identity or
privacy boundaries:

- the sidecar recorded `ready` immediately before opening its SSE stream, so
  sufficiently fast native input could finish before observation began;
- OpenCode emitted a completed assistant `message.updated`, then a trailing
  `session.status=busy`, then idle. The observer erased the completed candidate
  on that corroborating busy status and therefore lost the Fork boundary.

The corrected readiness barrier opens the exact SSE stream before publishing
`ready`. A completed assistant candidate survives busy status and polling until
exact idle corroboration; only a new incomplete message update clears it. No
message ID is derived from polling, message content, title, time ordering, or
session discovery.

The SSH run also showed that the former eight-second outer control timeout was
shorter than the adapter's bounded endpoint and observer-readiness gates.
Read-only and non-Runtime control remains capped at eight seconds. Only
Runtime-creating and recovery mutations use a bounded 45-second process
deadline; SSH connection setup remains at eight seconds and no persistent
control process was introduced.

## Contract-based compatibility correction

The first production implementation treated the acceptance-tested `1.18.11`
release as an exact allowlist. A post-acceptance correction removed that
release-number gate: bounded installation detection now treats version output
as diagnostic only, and the owned endpoint's reported version is retained only
as an opaque fingerprint that must remain stable within one Runtime generation.

Compatibility is enforced at the actual API/process boundaries: health shape,
root-session identity, SSE framing and events, settled message boundary, Fork
response, endpoint ownership, and exact cleanup. The disposable fake-provider
and mixed-provider suites advertise deliberately different future/development
version strings while satisfying those contracts. Missing or malformed health
metadata and a changed version within one generation fail closed. The real
local/SSH rerun records the installed release without using it as an admission
gate.

## Retained limits

Rename, native in-TUI session rebinding, arbitrary session adoption, and
cross-provider Fork remain unavailable. Because the accepted OpenCode Fork
contract exposes no structural lineage, a lost Fork response may leave an
unmanaged provider session for native inspection or cleanup; WSNav never
guesses, adopts, or retries it.

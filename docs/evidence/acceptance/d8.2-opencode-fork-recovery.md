Status: pass — 2026-08-06.

## Acceptance-driven corrections

The first run exposed two real lifecycle races without relaxing identity or
privacy boundaries:

- the sidecar recorded `ready` immediately before opening its SSE stream, so
  sufficiently fast native input could finish before observation began;
- OpenCode emitted a completed assistant `message.updated`, then a trailing
  `session.status=busy`, then idle. The observer erased the completed candidate
  on that corroborating busy status and therefore lost the Fork boundary.

The corrected readiness barrier opens the exact SSE stream before publishing
`ready`. A completed assistant candidate survives busy status and polling until
exact idle corroboration; only a new incomplete message update clears it. No
message ID is derived from polling, message content, title, time ordering, or
session discovery.

The SSH run also showed that the former eight-second outer control timeout was
shorter than the adapter's bounded endpoint and observer-readiness gates.
Read-only and non-Runtime control remains capped at eight seconds. Only
Runtime-creating and recovery mutations use a bounded 45-second process
deadline; SSH connection setup remains at eight seconds and no persistent
control process was introduced.

## Deterministic failure and final gates

The disposable fake-provider acceptance additionally proves the exact fork
request body, a trailing busy-before-idle event sequence, stream establishment
before observer readiness, distinct destination binding, exact-session
recovery, and terminal `external_effect_unknown` behavior when the provider
creates a destination but drops the response. That lost response issues no
retry, creates no WSNav destination, and leaves the source unchanged.

The final `scripts/check` gate passed 329 all-target Rust tests, formatting,

and staged/unstaged diff checks.

The recorded evidence contains no prompt or response text, terminal capture,

## Retained limits

OpenCode remains pinned to the explicitly accepted `1.18.11` release. Rename,
native in-TUI session rebinding, arbitrary session adoption, and cross-provider
Fork remain unavailable. Because this OpenCode release exposes no structural
Fork lineage, a lost Fork response may leave an unmanaged provider session for
native inspection or cleanup; WSNav never guesses, adopts, or retries it.
